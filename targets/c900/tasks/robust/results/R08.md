## Summary
Completed adversarial security, robustness, and invariants review of `client/c900-android/core/src/main/kotlin/rewatch/c900/*.kt`.
No paths exist to construct blocked or un-allowlisted commands, bypass GATT target restrictions, or initiate automatic Bluetooth bonding without explicit user consent.
Identified 5 operational findings: race condition in asynchronous GATT characteristic read completion (`Session.kt`), premature cancellation of in-flight commands upon receiving mismatched ACKs (`CommandQueue.kt`), short UUID parsing bounds crash (`Session.kt`), unbounded memory accumulation in `Session.inbound`, and synchronous multi-piece write dispatching without inter-chunk pacing in `CommandQueue.kt`.
All items from R08 scope evaluated and classified with failure stories and proposed fixes.

## Findings table
| ID | Severity | File:Line | Failure Story | Proposed Fix | Test That Would Catch It |
|---|---|---|---|---|---|
| F-01 | HIGH | `Session.kt:44-49` | Characteristic reads on Android BLE complete asynchronously. If battery read (`00002a19`) completes before hardware revision (`00002a27`), `ver` is still `null`, causing `Session` to fail with `Action.Fail("ver null not reviewed")` and abort setup. | Track completion of all required reads (`2a27`, `2a28`, `2a19`, `2a26`) using a remaining set; evaluate `ver` and transition to `READY` only once all reads have reported. | Call `readResult("...2a19...", byteArrayOf(50))` before calling `readResult("...2a27...", "10000".toByteArray())`. |
| F-02 | MEDIUM | `CommandQueue.kt:37` | If an unsolicited or delayed ACK arrives from the watch for an earlier command while a new command is in flight, `onAck` immediately fails the in-flight command with `"unexpected ack"` and purges it, rather than discarding the stale ACK. | Ignore mismatched ACKs when a command is in flight (or log debug warning) and allow in-flight command to continue waiting for its true matching ACK until timeout. | Submit command A, send ACK for command B: command A should remain in flight until its matching ACK or timeout. |
| F-03 | MEDIUM | `Session.kt:38` | Calling `readResult` with a short 16-bit UUID (e.g. `"2a27"`, length 4) throws `StringIndexOutOfBoundsException` because code unconditionally executes `uuid.lowercase().substring(4, 8)`. | Normalize UUID string with padding/regex or check `uuid.length >= 8` before substring extraction. | `s.readResult("2a27", "10000".toByteArray())` throws out of bounds exception. |
| F-04 | LOW | `Session.kt:22,65` | Inbound commands from notifications are appended unconditionally to `inbound` (`ArrayList<Frames.Inbound.Cmd>`) without maximum bounds or retention limits. In long-running sessions receiving streaming telemetry, this causes unbounded memory growth. | Cap `inbound` list with a ring buffer / eviction size limit (e.g. max 500 items), or expose as an event callback stream without retaining all past instances. | Feed 100k commands to `onCommand`; observe memory growth in `inbound`. |
| F-05 | LOW | `CommandQueue.kt:72` | `pieces.forEach { writes++; write(it) }` writes all chunks of a multi-piece frame synchronously in a tight loop. On Android BLE, calling `writeCharacteristic` in rapid succession drops subsequent writes or violates the 20 ms ATT inter-chunk pacing requirement (`Gatt.PIECE_GAP_MS`). | Clarify contract that caller write adapter must handle asynchronous queueing/delay, or implement chunk-by-chunk stepping in `CommandQueue`. | Inspect `write` invocations for a 2-piece message: both chunks emitted at timestamp delta 0 ms. |
