## Summary
The vendor app does not run periodic background timers for time sync or device settings.
Time sync (cmd 2 key 1) is written exactly once during the initial connect sync sequence (after cmd 2 key 10 pairing ACK) and on explicit user UI click.
Notification push (cmd 2 key 18) truncates payload text to 196 UTF-8 bytes (`Utils.subBytes(..., 196)`), queues up to 5 messages while disconnected (`msgList.size() > 4`), and gates writes on `dataType == DataType.GENERAL` and non-OTA state.
Settings builders (12/24h, alarms, step goal, units) write only on user UI save or during the connect sync sequence, with language writes guarded by `BleDataUtils.languageCode != newCode`.
A client rate-limiting budget based on vendor behavior is proposed.

## Proposed client limits
Based on empirical vendor behavior and ground rule 7 (protect device flash / avoid firmware hangs):
1. **Time sync:** Send at most once per connection. On system time/timezone change, debounce to at most once per 60 seconds.
2. **Notification push:**
   - Text limit: Truncate title + body to at most 196 bytes UTF-8 before formatting frame.
   - Queue limit: Retain at most 5 pending notifications while disconnected; drop oldest on overflow.
   - Rate limit: Minimum 500 ms inter-message delay between distinct notification frames.
   - Pacing: Slice multi-packet frames to 20-byte chunks 20 ms apart.
   - Guard: Pause notification push while syncing history (`dataType != GENERAL`) or during OTA.
3. **Find watch:** Minimum 3 seconds cooldown between successive find-device triggers.
4. **Settings (12/24h, alarms, step goal):** Write only when value differs from current cache; no periodic re-writing.
5. **Session write budget:** Retain a safe ceiling of 200 writes per session as a safeguard against runaway loops.
