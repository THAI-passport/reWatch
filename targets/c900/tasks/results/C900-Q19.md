## 2. Decision Tree Evaluation (NEXT-STEPS §4)

### 1. Connection & Transport (Q02)
- Peripheral connects to custom Nordic UART Service: `6E400001-B5A3-F393-E0A9-E50E24DCCA9F` [H].
- TX handle writes to `6E400002-...` [H].
- RX handle receives notifications on `6E400003-...` [H].
- No other transport (e.g. JieLi RCSP) was used.

### 2. Device Information Reads
During connection establishment, the app reads:
- `0x2A27` Hardware Revision: `"10000"` [H]
- `0x2A26` Firmware Revision: `"10000"` [H]
- `0x2A25` Serial Number: `<redacted len=8>` [H]
- `0x2A19` Battery Level: `26%` (later drops to `25%`) [H]

### 3. Wire Version Byte
- The app stores `10000` as an integer and casts it to a single byte: `10000 & 0xFF = 16 = 0x10` [H].
- Every outgoing frame generated by Hiwear Plus carries `0x10` at index 5:
  `DF 00 len sum cmd 10 key ...`
- The watch transmits `0x01` at index 5 on its outgoing frames:
  `DF 00 len sum cmd 01 key ...`
- **Impact on Client:** The frame builder must support `ver = 0x10` as a parameter when speaking to this device family.

### 4. Feature Map
- Read via `cmd 0x19 key 0`: marker `0xAA`, length 27 bytes [H].
- Raw hex: `aacfe081dff6fc3800000000000010e64108cf1400000000000000` [H].
- Decoded bits:
  - `isBLE3 = True` (bit 1 `0x80`)
  - `isSupportPair = True` (bit 15 `0x40`)
  - `binPreviewFlag = False` (bit 18 `0x20`)
  - `hideHrAndDnd = False` (bit 25 `0x80`)

### 5. Bonding & Pairing Behavior (Q03)
- The watch does **not** issue link-layer SMP security requests unprompted.
- Instead, application-level bonding is triggered:
  1. The app finishes initial setup (time sync, matching, step goal).
  2. The watch proactively notifies `DF cmd 0x0E key 1 ver 1 plen 6` carrying its Classic Bluetooth MAC address: `XX:XX:XX:XX:XX:XX`.
  3. Receiving `0x0E key 1` triggers Android `BluetoothDevice.createBond()` on the phone to bind Classic audio.
  4. App ACKs `FD cmd 0x0E key 1 x=0 status=1`.

## 4. ACK Value Formula Confirmed

Every ACK frame generated by the watch follows:
```text
FD 00 05 <checksum> <cmd> <key> <x_hi> <x_lo> <status>
```
Where:
- `status = 0x01` (success).
- `x = (x_hi << 8) | x_lo = plen + 9` where `plen` is the payload length of the command being acknowledged:
  - Time sync (`plen = 4`): `x = 4 + 9 = 13` (`0x000D`)
  - Real-time steps (`plen = 1`): `x = 1 + 9 = 10` (`0x000A`)
  - Bind token (`plen = 8`): `x = 8 + 9 = 17` (`0x0011`)
  - Message push (`plen = 28`): `x = 28 + 9 = 37` (`0x0025`)
  - Message push (`plen = 13`): `x = 13 + 9 = 22` (`0x0016`)

This resolves SimWatch's `[I]` ack formula with `[H]` exact evidence.

## 6. Review (Claude, 2026-10-13, from this file only; raw capture not seen)
1. **Privacy:** the watch OUI was kept in three places (`41:42:D0`-style); masked fully here, in LOG.md and docs/steps.md. History keeps it at 91bb5c0 (owner decides). The bind token, message text and serial stayed redacted: good. `tools/privacy_scan.py` now reports 0 findings on the repo docs.
2. **Time sync was mis-described** as a big-endian Unix timestamp. Decoding `6a9b05cb` with the I-21 packing gives 2026-10-13 16:23:11, the capture day; as Unix seconds it would be 2026-09-04. `frames.time_payload(2026,10,13,16,23,11)` reproduces the bytes exactly. So I-21 is now [H].
3. **Version byte 0x10 [H]** on all 63 app frames; the watch uses 0x01. The int-to-byte cast is the explanation [I]; the wire value is what matters for the codec.
4. **Ack x:** `x = plen + 9` is exactly the total length of the acknowledged frame (len + 4 = plen + 5 + 4). Better name: "acked frame length", not a sequence number. Replaces SimWatch's `00 01` guess (I-18).
5. **Bonding:** the 0x0E key 1 frame is [H] (three times). That the phone then bonded the Classic link is app-side [C]; confirming it needs the HCI auth/SMP events from the same capture (next decode pass). Time-sync ack + b15 0x40 path (I-30 #2) not checked either.
6. Feature map here equals the live-session 0x2A28 read byte for byte: consistent [H].
