# C900-Q07 — OTA ready reply (0x81) and CRC edge cases (documentation only)

Date: 2026-10-13 (Asia/Saigon). Static only (jadx + smali of `OTANotifyWriteUtils`, `OTAUtils`, `CommandUtils`). Status: **done**.

**Client rule: the client must not implement any of this.** No OTA, face, paper or contact transfer; no writes to 0xFF00 / 0xFF02 / 0x18A8 (PROTOCOL §6, ground rule 7, C900-D05/D06).

## Answer: 300 vs 500 ms
Both numbers are real, and neither one paces the transfer [C smali]:
- **500 ms** is the field initializer: `OTANotifyWriteUtils.<init>` stores `const/16 0x1f4` into `sendInterval`. jadx printed it as `CropImageView.DEFAULT_IMAGE_TO_CROP_BOUNDS_ANIM_DURATION`, a library constant with the same value.
- **300 ms** is the substitute when the watch's 0x81 reply carries interval 0: `if-nez ... const/16 0x12c`.
- The only read of `sendInterval` in the whole app is the log line in `dataHandle`; `getSendInterval()` has no callers (smali search across all dex dirs).
- What actually paces D6 data: each queued frame waits **10 ms** (`Thread.sleep(0xa)`) and the next frame is released only by the BLE write-complete callback (`OTANotifyWriteUtils.onWrite(true)` pops the queue). A failed write disconnects.
So "default 300 if 0; field init is 500" in PROTOCOL §6.3 was accurate as a description of the field, but misleading as a timing rule. The watch's interval value is ignored by this app version.

## Inbound D5 reply layout [C, `OTANotifyWriteUtils.dataHandle`]
`D5 main sub fun b4 status plen_hi plen_lo payload... sum`; total length = `plen + 9`. Fun at byte 3, status/error code at byte 5, payload from byte 8. **The app does not verify the reply checksum.** An inbound frame starting with D6 aborts the transfer.

| fun | Meaning | Fields | Tag |
|---|---|---|---|
| 0x81 | ready reply to `startOTA` | bytes 8-9 `deviceMtu` u16 BE; 10-11 `sendInterval` u16 BE (logged only); 12 `groupPacNum`; 13 timeout units (x 5000 ms) | [C smali: `aget-byte` 8..13, `mul-int/lit16 0x1388`] |
| 0x81 short (< 14 bytes) | refusal | byte 5 = 13 -> "watch face picture too large" broadcast; any short reply aborts | [C] |
| 0x82 | group CRC result | byte 5 = 0 -> next group; else abort | [C] |
| 0x83 | file CRC result | byte 5 = 0 -> finish; else abort | [C] |

Width edge cases [C smali]: `groupPacNum` and the timeout byte are read with signed `aget-byte`, so values >= 0x80 become negative (group count <= 0, negative timeout). `deviceMtu` and interval are masked with 0xff per byte, so they are unsigned.

## Outbound control frames (confirmation of PROTOCOL §6.3)
- `startOTA(main, sub, fun=1, mtu, len)`: the advertised mtu is `MBleManager.getPeripheralMtu() - 3` (the negotiated ATT MTU minus 3), not a fixed 182 [C].
- Group CRC fun=2 and file CRC fun=3 carry one byte each [C].
- Data frame: `D6` + chunk of `deviceMtu - 1` bytes; a frame longer than `deviceMtu` is silently not written, and the timeout then disconnects [C].

## Timers [C smali]
| Timer | Value | Where |
|---|---|---|
| Per-frame write guard | `timeOut`: 10 s at init (`0x2710`), then `units x 5000` from 0x81; armed after each control-frame write and cancelled by the write callback, so it guards the write, not the watch reply | `OTANotifyWriteUtils` |

| Pre-0x81 defaults | `deviceMtu` 20, `groupPacNum` 1 | `<init>` |

## CRC (confirmation) [C, `OTAUtils.sendData`]
Per data byte `x`: group accumulator `g ^= x`, file accumulator `f ^= x`, then 8 rounds on each: `acc = (acc & 0x80) ? (acc << 1) ^ 0x31 : acc << 1`. Only `acc & 0xff` is sent. The group accumulator restarts at 0 per group; the file accumulator runs over the whole file. Note: the accumulators are Java ints and are not masked between rounds, so high bits grow; this does not change the low 8 bits, because the `0x80` test only looks at bit 7, and bits above 7 never shift back down [I, arithmetic].

## Contradictions
- PROTOCOL §6.3 "default 300 if 0; field init is 500" is correct about the field but implied a send interval. Corrected: the interval is never applied (recorded in FACTS).
- None with FACTS.md otherwise.
